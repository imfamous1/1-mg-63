## 1. Жизненный цикл программного проекта и Agile-подходы

**Жизненный цикл программного проекта (SDLC)** — это совокупность этапов, через которые проходит программный продукт: анализ требований, проектирование, реализация, тестирование, внедрение, эксплуатация и сопровождение. В классических моделях (водопад, каскадная) этапы идут последовательно, а возврат назад ограничен.

**Agile-подходы** (Scrum, Kanban и др.) делают акцент на итеративной разработке, быстрой обратной связи и готовности к изменениям. Проект разбивается на короткие спринты (обычно 1–3 недели), в конце каждого спринта команда показывает работающий инкремент продукта. Планирование ведётся по бэклогу задач.

Для планирования и отслеживания задач используются электронные доски:

- Jira — промышленный стандарт для управления Agile-процессами в компаниях.
- Trello — более простой инструмент с досками и карточками, подходящий для учебных и небольших проектов.

На доске задачи обычно имеют статусы («Запланировано», «В работе», «Готово»), назначенных исполнителей и приоритеты.

## 2. Архитектуры и современные веб-приложения

### 2.1. Монолит и микросервисы

**Монолитная архитектура** — приложение разворачивается как один целый блок: весь код (модули, слои) собирается в единый артефакт и разворачивается одновременно.

- Преимущество: проще начать, меньше инфраструктурных зависимостей.
- Недостаток: со временем усложняется сопровождение; сложно масштабировать отдельные части.

**Микросервисная архитектура** — система состоит из набора независимых сервисов, каждый отвечает за свою область ответственности и взаимодействует с другими по сетевым протоколам (обычно HTTP/REST).

- Преимущество: независимое развёртывание и масштабирование, гибкость.
- Недостаток: выше сложность инфраструктуры, нужны решения для логирования, мониторинга, аутентификации между сервисами.

### 2.2. SPA и MPA

**Многостраничное приложение (MPA)** — классический подход: для каждой страницы браузер запрашивает отдельный HTML-документ у сервера. Навигация сопровождается полной перезагрузкой.

**Одностраничное приложение (SPA)** — основная HTML-страница загружается один раз, дальше контент подгружается и перерисовывается на стороне клиента (JavaScript). Навигация имитируется с помощью изменения состояния приложения и History API.

- Плюсы SPA: более плавный пользовательский опыт, меньше полных перезагрузок.
- Минусы SPA: больше сложность на фронтенде, требуется проработка SEO и начальной загрузки.

В учебном курсе акцент делается на понимании принципов (структура HTML, работа DOM, навигация), а не на конкретных фреймворках.

## 3. Git и основы командной разработки

**Git** — распределённая система контроля версий. Позволяет хранить историю изменений, переключаться между версиями, работать в ветках и объединять (merge) результаты работы разных разработчиков.

Базовые команды:

- `git clone` — клонирование удалённого репозитория (создание локальной копии).
- `git add` — добавление изменённых файлов в индекс (staging area) перед коммитом.
- `git commit` — фиксация изменений в локальной истории с сообщением.
- `git push` — отправка локальных коммитов на удалённый репозиторий (например, GitHub).

Работа с Git и GitHub обязательна для курсовых и практических проектов: код должен быть версионируемым и доступным для проверки.

## 4. REST API и HTTP-методы

**REST API** — стиль взаимодействия клиент–сервер, основанный на использовании стандартных HTTP-методов и чётко определённых ресурсов (URL).

Основные методы:

- `GET` — получение ресурса (чтение данных).
- `POST` — создание нового ресурса или выполнение действия.
- `PUT` / `PATCH` — полное или частичное обновление ресурса.
- `DELETE` — удаление ресурса.

Клиент (браузер, JS-код) отправляет запросы, сервер возвращает статус-код (например, `200 OK`, `404 Not Found`, `500 Internal Server Error`) и данные (часто в формате JSON). В учебных проектах REST используется для работы с внешними API (например, данные о погоде, справочники) или имитации обмена данными.

## 5. Промпт-инжиниринг и генеративный ИИ

**Промпт-инжиниринг** — практика продуманной формулировки запросов к генеративным моделям (ChatGPT, DeepSeek, Claude и др.) с учётом цели, ограничений и нужного формата ответа.

Ключевые принципы:

- Чётко указывать цель и ограничения (стек технологий, формат ответа, наличие/отсутствие фреймворков).
- Разбивать задачу на шаги (структура → стили → JS → полировка).
- Давать модели контекст проекта (существующие файлы, требования).

Генеративный ИИ в курсе выступает как помощник: черновики кода, идеи для интерфейса, генерация текстов. Результат всегда проверяется и при необходимости дорабатывается вручную.

## 6. Машинное обучение, нейронные сети и LLM

**Машинное обучение** — область ИИ, в которой алгоритмы обучаются по данным, а не программируются явно. Модель получает примеры «вход–выход» и подстраивает параметры для минимизации ошибки.

**Нейронные сети** — класс моделей машинного обучения, вдохновлённый структурой биологических нейронов. Они особенно хорошо работают с изображениями, текстом и сложными многомерными данными.

**Генеративные модели и LLM** (Large Language Models) — нейросети, обученные на больших объёмах текста и/или кода, способные генерировать новые тексты, фрагменты кода, описания интерфейсов. В курсе они используются для:

- генерации и объяснения HTML/CSS/JS;
- поиска и исправления ошибок;
- подготовки теоретических конспектов и вариантов ответов на вопросы.

Важно понимать ограничения: возможны неточности и «галлюцинации», поэтому без проверки такие ответы нельзя считать авторитетным источником.

## 7. CI/CD и инженерные практики

**CI (Continuous Integration)** — непрерывная интеграция: частое объединение изменений в общую ветку, автоматический запуск тестов и проверок качества кода. Цель — быстро находить ошибки при интеграции.

**CD (Continuous Delivery/Deployment)** — непрерывная поставка/развёртывание: автоматизация доставки изменений до среды тестирования и/или боевой среды.

Для учебных проектов базовый уровень CI/CD может включать:

- автоматическую проверку сборки проекта (линтеры, тесты);
- автоматическую публикацию статического сайта (GitHub Pages) при пуше в определённую ветку.

Эти практики напрямую связаны с надёжностью и повторяемостью развёртывания приложений, в том числе в сфере безопасности.

## 8. DOM и работа JavaScript с веб-страницей

**DOM (Document Object Model)** — объектное представление HTML-документа в памяти браузера. Каждому тегу соответствует узел (node), JS может получать к нему доступ, читать и изменять его свойства.

Типовой цикл работы:

- поиск элементов (`document.querySelector`, `querySelectorAll`, `getElementById` и др.);
- изменение содержимого (`textContent`, `innerHTML`), стилей (`style`, классы);
- обработка событий (`addEventListener`).

Знание DOM необходимо для реализации практических заданий: форм, таблиц, списков дел (To‑Do), счётчиков, выпадающих списков и т.д.

## 9. Адаптивный веб-дизайн

**Адаптивный веб-дизайн** — подход, при котором интерфейс корректно отображается на экранах разного размера (телефон, планшет, десктоп).

Основные инструменты:

- **Медиа-запросы** (`@media`) — изменение стилей в зависимости от ширины/высоты экрана.
- **Flexbox и Grid** — современные способы построения гибких сеток и раскладок.
- **Mobile-first** — сначала верстается мобильная версия, затем добавляются стили для более широких экранов.

Адаптивность важна для пользовательского опыта и зачастую прямо входит в требования к курсовому проекту.

## 10. Базы данных и СУБД

**База данных** — организованная совокупность структурированной информации.

Основные этапы проектирования:

1. Анализ предметной области и требований.
2. Определение сущностей (таблиц) и связей между ними.
3. Определение полей, типов данных, ключей.
4. Нормализация схемы (устранение избыточности).

**СУБД (система управления базами данных)** — программное обеспечение, обеспечивающее хранение, поиск, изменение и защиту данных (MS Access, PostgreSQL, MySQL и др.). В контексте РПД отдельно упоминается MS Access как пример универсальной СУБД.

Для дисциплины важен концептуальный уровень: понимание таблиц, полей, типов данных, запросов и того, как БД может поддерживать информационные ресурсы и системы безопасности.

## 11. Угрозы информационной безопасности веб-приложений

К основным угрозам относятся:

- **XSS (межсайтовый скриптинг)** — внедрение вредоносного JS в страницу (например, через неэкранированный ввод пользователя).
- **SQL-инъекции** — вредоносные запросы к базе данных через поля ввода.
- **Кража учётных данных** (фишинг, слабые пароли).

Типичные меры защиты:

- валидация и экранирование пользовательского ввода;
- использование подготовленных выражений (prepared statements) при работе с БД;
- корректная настройка прав доступа, HTTPS, защита cookies (HttpOnly, Secure).

Для дисциплины важно понимание общих принципов угроз и базовых мер защиты, даже если сложная серверная часть не реализуется.

## 12. Облачные технологии

**Облачные технологии** — модель предоставления вычислительных ресурсов (серверы, хранилище, базы данных, сервисы) через Интернет по запросу.

Основные модели:

- IaaS (инфраструктура как сервис) — виртуальные серверы, сети, хранилища.
- PaaS (платформа как сервис) — готовая платформа для развёртывания приложений.
- SaaS (ПО как сервис) — готовые приложения (почта, офисные пакеты, системы управления проектами).

В контексте курса облака интересны как платформа для размещения информационных ресурсов и сервисов, связанных с техносферной безопасностью (мониторинг, оповещение, аналитика).

## 13. Техносферная безопасность и роль ИТ

**Техносферная безопасность** — область, изучающая защиту человека и окружающей среды от негативных воздействий техногенных процессов и объектов.

Примеры применения ИТ:

- системы мониторинга состояния среды (качество воздуха, воды, шум, вибрации);
- платформы оповещения населения о ЧС;
- обучающие веб-ресурсы и симуляторы действий в нештатных ситуациях;
- аналитические системы для оценки экологических и техногенных рисков.
