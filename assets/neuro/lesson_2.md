# Промпт-инжиниринг: формулировка запросов и работа с контекстом проекта

В лекции рассматриваются принципы формулировки запросов к LLM (промптов), правила, повышающие качество ответа, роль контекста проекта, а также рекомендуемый порядок работы над сайтом и примеры промптов для типовых задач веб-разработки.

## 1. Что такое промпт

**Промпт** — это текстовый запрос к модели, передаваемый через чат, среду разработки (IDE) или API. В контексте разработки промпт по сути выполняет роль технического задания: чем яснее сформулированы цель, ограничения и ожидаемый формат ответа, тем выше вероятность получить пригодный результат. Формулировка промпта напрямую влияет на то, насколько ответ модели будет соответствовать задаче и структуре проекта.

## 2. Правила формулировки промпта

Целесообразно придерживаться следующих правил.

**Указание цели и ограничений.** Вместо расплывчатых формулировок («сделай красивую страницу») следует задавать конкретику: технологический стек (чистый HTML/CSS/JS, без фреймворков), требования к адаптивности (mobile-first), состав разделов и желаемое поведение (например, навигация без перезагрузки страницы). Пример удачной формулировки: «Сделай одностраничный сайт на чистом HTML/CSS/JS, mobile-first, без фреймворков. Разделы: Лекции, Практики, Экзамен. Навигация без перезагрузки».

**Пошаговое разбиение задачи.** Рекомендуется идти слоями: сначала структура (семантический HTML), затем визуальное оформление (CSS), затем поведение (JavaScript), при необходимости — полировка (адаптивность, доступность, исправление ошибок). Отдельный запрос на каждый слой упрощает контроль результата и снижает риск того, что модель «уйдёт» в сторону.

**Указание формата ответа.** Полезно явно просить нужный формат: «Дай только код для `js/main.js` без пояснений», «Напиши патч: что удалить и что добавить», «Выдай только новый фрагмент кода для секции, не переписывая весь файл». Это уменьшает объём лишнего текста и упрощает вставку кода в проект.

**Критерии проверки.** Имеет смысл кратко описать ожидаемый результат: «После изменений при клике на „Лекции“ отображается список частей; при клике на урок загружается .md и показывается внутри страницы; в консоли ошибок нет». Так модель лучше ориентируется на целевое поведение, а вы можете проверить соответствие ответа задаче.

## 3. Роль контекста проекта

Качество ответа LLM сильно зависит от **контекста** — того, что модель «видит» в запросе. Релевантный контекст включает: текущие файлы проекта (`index.html`, `css/style.css`, `js/main.js`, `index.json`), заявленные требования (mobile-first, без внешних библиотек) и текущее состояние (что уже реализовано, что нужно изменить). Если контекста недостаточно, модель вынуждена догадываться о структуре проекта и часто даёт ответы, которые не стыкуются с существующим кодом. Поэтому при доработке сайта целесообразно прикладывать к запросу нужные файлы или их фрагменты.

## 4. Последовательная работа над сайтом

Рациональный подход — не просить «сделать сайт заново», а формулировать точечные задачи и давать модели актуальное состояние проекта. После того как базовая версия сайта с навигацией готова, добавление новой секции или функции лучше строить так: передать модели текущие файлы (или ключевые фрагменты), чётко описать, что нужно добавить или изменить, и попросить выдать только новый код с указанием места вставки. Так снижается риск того, что модель перепишет значительную часть проекта; изменения проще проверить и интегрировать.

## 5. Примеры промптов для типовых задач

Ниже приведены примеры формулировок, которые можно использовать как шаблоны и адаптировать под свой проект.

**Добавление секции в HTML (только новый код).** «У меня сайт на чистом HTML/CSS/JS. Вот `index.html` (вставляю файл). Добавь новую секцию `<section>` для блока „FAQ“ (три вопроса). Не переписывай весь файл. Дай только новый HTML и укажи точное место вставки (между какими строками или блоками).»

**Добавление стилей (минимальные изменения).** «Вот `css/style.css` (вставляю). Добавь стили для секции FAQ: карточки, отступы, аккуратная типографика. Сделай mobile-first, без библиотек. Дай ответ в формате: что добавить в конец файла.»

**Добавление интерактивности (ванильный JavaScript).** «Вот `js/main.js` (вставляю). Сделай так: клики по вопросу в FAQ раскрывают или скрывают ответ (аккордеон). Без библиотек. Пиши только новый код: какие функции добавить и куда вставить, чтобы не нарушить существующую навигацию.»

**Использование контекста проекта.** «У меня одностраничный сайт на HTML/CSS/JS. В проекте уже есть `index.json` с разделами (Лекции, Практики, Экзамен) и списком материалов. Добавь на главную блок „Быстрые ссылки“: по одной ссылке из каждого раздела (первый пункт из каждого). Данные брать из существующего `index.json`, не хардкодить. Дай только новый фрагмент HTML (где блок вставить) и код для `js/main.js` (как подставить ссылки), не переписывай весь файл.»

**Генерация страницы под ключ.** «Создай одностраничный сайт (HTML/CSS/JS, mobile-first) на тему „Информационные технологии в сфере безопасности“. Требования: три раздела, навигация без перезагрузки, контент в `index.json`. Стили лаконичные, читабельные, без фреймворков. Выдай структуру проекта и код файлов.»

## 6. Типичные ошибки и как их избегать

Модель нередко переписывает весь файл вместо точечных правок — заранее указывайте «не переписывай» и просите дифф или явное указание места вставки. Модель может подключать сторонние библиотеки — явно задавайте ограничения: «без библиотек», «ванильный JS». Чтобы не нарушить существующую логику, формулируйте запрос так: «не трогай существующие функции, добавь рядом новую». Проверка результата в браузере и в коде остаётся обязанностью разработчика.

## Связь с последующим материалом

Полученные навыки формулировки промптов и работы с контекстом применяются в практических заданиях: выберите одну небольшую доработку (секция, стили или функция на JavaScript) и выполните её за 2–3 итерации запросов к LLM, фиксируя результат в файлах проекта.
