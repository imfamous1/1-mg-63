# Промпт-инжиниринг: как разговаривать с LLM при разработке сайта

В этой лекции делается акцент не на теории нейросетей, а на **практике работы с промптами**: как именно формулировать запросы к LLM, чтобы она помогала делать сайт под требования дисциплины, а не генерировала абстрактные примеры. Материал подан в виде чек‑листов, шаблонов и готовых формулировок, которые можно брать и адаптировать под свои задачи.

## 1. Что такое промпт в контексте курса

**Промпт** — это управляемое текстовое задание для модели, по сути мини‑ТЗ:

- **где** вы работаете: чат, IDE, веб‑интерфейс;
- **какую задачу** решаете: создать страницу, поправить блок, найти ошибку;
- **какие ограничения** важны: чистый HTML/CSS/JS, без фреймворков, mobile‑first;
- **какой формат ответа** нужен: целый файл, фрагмент кода, дифф;
- **какие файлы и контекст** вы прикладываете.

От качества промпта напрямую зависит, получите ли вы код, который реально можно вставить в свой проект, а не «демо»-страницу «где‑то в вакууме».

## 2. Структура хорошего промпта

Практически любой запрос к модели для задач по сайту можно разложить на одну и ту же структуру:

1. **Роль и контекст**
   - кто вы и что делаете: «я делаю учебный сайт по дисциплине…»;
   - какие есть файлы: `index.html`, `css/style.css`, `js/main.js`, `index.json`.
2. **Цель**
   - что именно должно измениться в результате: «добавить секцию», «починить навигацию», «сделать адаптив».
3. **Ограничения**
   - стек: только HTML/CSS/JS;
   - без библиотек и фреймворков;
   - не переписывать весь файл.
4. **Формат ответа**
   - «дай только новый фрагмент кода»;
   - «сделай патч: что удалить, что добавить»;
   - «не добавляй пояснений, только код».
5. **Критерии проверки**
   - что вы будете считать успехом: «после клика открывается…», «в консоли нет ошибок», «страница корректно смотрится на телефоне».

Хороший промпт — это не длинный, а **структурированный** текст.

## 3. Чек‑лист перед отправкой промпта

Перед тем как нажать «Отправить», пробегитесь по мини‑списку:

- **Я описал(а) текущую ситуацию?**
  - «У меня есть одностраничный сайт на HTML/CSS/JS, вот `index.html` и `index.json`…»
- **Я явно задал(а) ограничения?**
  - «Без фреймворков, без библиотек, мобильная версия важнее настольной».
- **Я сказал(а), что именно нужно изменить, а не „сделать красиво“?**
  - «Добавь секцию отзывов под блоком X», «сделай плавный скролл по якорям».
- **Я запросил(а) удобный для меня формат ответа?**
  - «Только код для `js/main.js` без комментариев».
- **Я понимаю, как проверю результат?**
  - «Открою страницу, кликну по ссылке, посмотрю консоль».

Если на какой‑то пункт ответ «нет», промпт стоит доработать.

## 4. Работа с контекстом проекта

Чтобы модель перестала «угадывать» структуру вашего сайта, ей нужно дать **реальный контекст**:

- прикладывать **существующие файлы целиком** (или ключевые фрагменты);
- явно указывать, какие части кода менять, а какие нельзя трогать;
- напоминать про структуру `index.json` (разделы Лекции, Практики, Экзамен).

Пример формулировки с контекстом:

> «У меня одностраничный сайт на чистом HTML/CSS/JS. Навигация и контент завязаны на `index.json` (разделы Лекции, Практики, Экзамен). Ниже прикладываю `index.html` и `js/main.js`. Добавь возможность по клику на пункт меню подгружать соответствующий `.md`‑файл и отображать его в основном контент‑блоке. Не переписывай существующую разметку шапки и футера».

Без такого описания модель почти неизбежно предложит «сделать всё заново».

## 5. Шаблоны промптов для сайта

Ниже — готовые формулировки в стиле «скопируй, подставь свои части».

### 5.1. Создание базовой структуры страницы

**Задача:** получить первый черновик страницы.

> «Сделай каркас одностраничного сайта на чистом HTML/CSS/JS без фреймворков. Тема: „Информационные технологии в сфере безопасности“. Разделы: Лекции, Практики, Экзамен. Сверху навигация по разделам, в центре — блок для контента раздела. Стили напиши в отдельном файле `css/style.css`, скрипты — в `js/main.js`. Сделай mobile‑first: чтобы на телефоне меню было столбцом, а на десктопе — по горизонтали. Дай код трёх файлов: `index.html`, `css/style.css`, `js/main.js`.»

### 5.2. Точечная доработка HTML

**Задача:** добавить новый блок, не ломая остальное.

> «Вот мой `index.html` (вставляю файл). Добавь под секцией „Практики“ новую секцию `<section>` „Частые вопросы“ с тремя вопросами и ответами. Не переписывай весь файл, не меняй существующие секции. Дай только новый HTML‑фрагмент и укажи, после какого блока его вставить.»

### 5.3. Добавление стилей

**Задача:** оформить уже существующую секцию.

> «Вот `css/style.css` (вставляю). Добавь стили для секции FAQ: светлые карточки с тенью, отступы, читаемый шрифт. Сделай mobile‑first, без библиотек. Ответ дай в формате: какой код добавить в конец файла CSS, без изменений существующих правил.»

### 5.4. Добавление интерактивности (vanilla JS)

**Задача:** «оживить» интерфейс.

> «Вот `js/main.js` (вставляю). Сделай так: при клике на вопрос в секции FAQ разворачивается ответ (аккордеон), при повторном клике — сворачивается. Не трогай существующие функции навигации по разделам, добавь новую логику ниже. Дай только новый код функций и обработчиков событий.»

### 5.5. Работа с `index.json`

**Задача:** использовать уже описанные в JSON материалы.

> «В проекте есть `index.json` со списком материалов (Лекции, Практики, Экзамен). Хочу блок „Быстрые ссылки“ на главной: по одной ссылке на первый материал из каждого раздела. Данные нужно брать из `index.json`, ничего не хардкодить. Вот `index.json`, `index.html` и `js/main.js` (вставляю). Дай фрагмент HTML для блока „Быстрые ссылки“ и код для `js/main.js`, который заполнит его на основе JSON.»

## 6. Промпты для отладки и рефакторинга

LLM полезна не только для генерации, но и для **разбора уже написанного кода**.

- **Поиск ошибок**
  > «Вот `js/main.js` (вставляю). После клика на пункт меню „Лекции“ у меня ничего не происходит. Посмотри код и найди возможные ошибки. Объяснения дай кратко, предложи патч в формате: какую строку удалить/изменить и какую вставить вместо неё.»

- **Улучшение читаемости**
  > «Возьми этот фрагмент JavaScript (вставляю). Перепиши его так, чтобы он был проще: более понятные имена переменных, меньше дублирования. Поведение менять нельзя. Дай только новый код функции.»

- **Проверка на соответствие требованиям курса**
  > «Вот мой `index.html` и `css/style.css`. Оцени с точки зрения учебного проекта: есть ли семантические теги, адаптивность, понятная структура. Перечисли коротким списком, что уже хорошо, и что стоит улучшить. Для каждого пункта улучшения предложи короткий пример кода или приём.»

## 7. Типичные ошибки в промптах и как их избежать

Распространённые ситуации:

- **Слишком общие формулировки.**
  - Плохо: «Сделай мне сайт по безопасности».
  - Лучше: чётко задать разделы, стек, ограничения.
- **Просьба «сделать всё заново».**
  - Плохо: «Перепиши сайт, чтобы он был лучше».
  - Лучше: «Исправь навигацию, не трогай остальное».
- **Отсутствие указания формата ответа.**
  - Плохо: «Сделай аккордеон».
  - Лучше: «Дай только новый код для `js/main.js`, без пояснений».
- **Нет прикреплённого контекста.**
  - Плохо: «У меня не работает JS».
  - Лучше: приложить сам файл и описать симптомы.

Правило: если по вашему промпту **человек‑разработчик** не смог бы однозначно понять задачу, модели тоже будет трудно.

## 8. Вместо заключения

На практике промпт‑инжиниринг лучше всего усваивается **во время реальной работы над сайтом**. Используйте приведённые выше шаблоны как отправную точку, адаптируйте формулировки под свой проект и фиксируйте удачные промпты отдельно — это быстро превратится в вашу личную «шпаргалку», к которой можно возвращаться при выполнении любых заданий.
